# ankb 実装指示書（Claude Code 向け）

> ankb = an AI-native knowledge base
> フロントエンド：WebMCP / バックエンド：サーバサイド MCP
> この文書は AI コーディングエージェントが実行することを前提に書かれている。記載のない判断が必要になった場合は、実装を止めて質問すること。

---

## 0. エージェントへの基本ルール

- 各ステップ（§10）は順番に実行し、ステップごとに「完了条件」を満たしてからコミットする。
- **権限（§5）とノートの状態（§4.2）に関わる仕様は変更禁止**。変更が必要だと判断した場合は理由を添えて提案し、承認を待つ。
- 技術スタック（§3）は前提値。より適した選択肢があれば、実装前に提案してよい。
- WebMCP は仕様策定中の API である。実装前に最新の仕様とブラウザ対応状況を確認し、差分があれば報告すること。
- 回答の合成に関するテスト（§9）が通らない変更はマージしない。

## 1. プロダクト概要

### 1.1 解く課題

個人〜小規模チームのナレッジは、ノート・議事録・チャットの転記メモなどに**断片として散らばり**、同じテーマのノートが複数あると**どれが今有効なのか判別できない**。その結果、必要な時に答えにたどり着けない。

### 1.2 提供価値

**散らばった断片から、今有効な答えを、根拠付きで組み立てる。**

- 複数ノートを横断して 1 つの答えにまとめる
- 各主張に根拠ノートを必ず添える
- 置き換え済みの古い情報は既定で答えから除外し、「旧情報」として区別して見せる
- 有効なノート同士の矛盾は隠さずに提示する

### 1.3 AI ネイティブの意味

ankb は人間とエージェントの両方を正式な利用者として扱う。

| 入口 | 利用者 | 特徴 |
|---|---|---|
| Web UI | 人間 | 通常の閲覧・編集・承認 |
| WebMCP | ブラウザ内エージェント | ユーザーが開いている画面の文脈を共有し、UI を操作する |
| サーバ MCP | 外部エージェント（Claude Code、Claude Desktop 等） | 画面を持たず、API として読み書きする |

**3 つの入口はすべて同じコアロジック（検索・有効性判定・権限）を通る。** 入口ごとに挙動が違う実装は禁止。

## 2. ペルソナ

### 2.1 人間（メインペルソナ：A と B の両立）

**A. 美咲 — 小規模チームのバックオフィス担当（非技術職）**
- 規程、手順、過去の対応履歴を探す
- 何という言葉で検索すればいいか思いつかない。自然文で質問したい
- 回答が正しいか自分で判断しづらいため、「どれが現行か」が明示されていることが重要
- 設計上の含意：専門用語を UI に出さない。承認操作はワンクリックで完結させる

**B. 健太 — PM・企画（個人用とチーム用を兼ねて使う）**
- 議事録や決定事項から「なぜそう決めたか」という経緯をたどる
- 自分用のメモとチームに共有するノートが混在している
- 設計上の含意：時系列での経緯の再構成、ノート単位の公開範囲の切り替え

**C. 翔 — エンジニア（サブペルソナ）**
- Claude Code での実装中に、サーバ MCP 経由で仕様や設計判断を参照する
- 設計上の含意：MCP ツールの返り値は機械が処理しやすい構造にする

### 2.2 エージェント

**D. ブラウザ内アシスタント（WebMCP 経由）**
- 美咲や健太が開いているページ（ノート、検索結果）を文脈にして動く
- UI を操作できる（ノートを開く、比較ビューを開く、引用箇所をハイライトする）
- 承認などの確定操作は、必ず人間の確認を UI 上で経由する

**E. 外部エージェント（サーバ MCP 経由）**
- 画面なしで、ユーザーの権限の範囲内で読み書きする
- 置き換え関係の「提案」はできるが、「承認」はできない

## 4. ドメインモデル

### 4.1 エンティティ

```
workspace        チーム単位の器。個人利用は 1 人の workspace として扱う
member           workspace と user の所属（role: owner | member）
note             ノート本体
note_version     ノートの編集履歴（本文スナップショット）
note_share       ノート単位の共有先（user 単位、permission: view | edit）
note_chunk       検索用の分割テキスト + embedding
note_relation    ノート間の関係（置き換え・矛盾・関連）
```

### 4.2 note の主要フィールド

| フィールド | 型 | 説明 |
|---|---|---|
| `status` | `draft \| active \| superseded \| archived` | 有効性の状態 |
| `visibility` | `private \| shared \| workspace` | 公開範囲（§5） |
| `owner_id` | uuid | 作成者 |
| `effective_from` | date, nullable | 内容が有効になる日（規程の施行日など）。任意 |
| `updated_at` | timestamptz | 最終更新 |
| `superseded_by` | uuid, nullable | 承認済みの置き換え先（非正規化キャッシュ） |

**状態遷移のルール**
- `active → superseded` は、`note_relation(type=supersedes, state=confirmed)` が作られた時**のみ**起こる。直接の書き換えは禁止
- 置き換え関係が取り消された場合は `superseded → active` に戻す
- `draft` は検索対象外（オーナー本人の検索を除く）

### 4.3 note_relation

| フィールド | 型 | 説明 |
|---|---|---|
| `from_note_id` / `to_note_id` | uuid | `from` が `to` を置き換える、などの向き |
| `type` | `supersedes \| contradicts \| related` | 関係の種類 |
| `state` | `proposed \| confirmed \| rejected` | 承認状態 |
| `proposed_by` | `ai \| user \| agent` | 提案元 |
| `confidence` | float, nullable | AI 提案時の確信度 |
| `rationale` | text | 提案理由（人間が読める日本語） |
| `resolved_by` / `resolved_at` | uuid / timestamptz | 承認・却下した人間と日時 |

## 5. 権限モデル（変更禁止）

### 5.1 公開範囲

| visibility | 閲覧できる人 |
|---|---|
| `private` | オーナーのみ |
| `shared` | オーナー + `note_share` に登録されたユーザー |
| `workspace` | workspace の全メンバー |

編集権限はオーナー、または `note_share.permission = edit` を持つユーザーのみ。

### 5.2 絶対に守るルール

1. **権限は DB の RLS で強制する。** アプリ層のフィルタだけに頼らない
2. **エージェントはユーザー本人の権限で動く。** サーバ MCP も WebMCP も、ユーザーのセッション／トークンで DB にアクセスする。サービスロールキーでの読み出しは禁止（バックグラウンドジョブを除く。§5.3）
3. **回答の合成には、質問者が閲覧できるノートだけを使う。** 閲覧できないノートの存在・タイトル・件数を回答や返り値に含めてはならない
4. **置き換え関係の提案・表示でも同じ。** 提案の相手ノートが閲覧できないユーザーには、その提案を見せない

### 5.3 バックグラウンドジョブの例外

置き換え候補の検出（§6.2）はサービスロールで動いてよい。ただし、生成した提案は §5.2 の 4 に従い、閲覧権限を持つユーザーにだけ表示する。

## 6. コア機能

### 6.1 検索パイプライン（全入口で共通）

```
質問
 → クエリ展開（言い換え・同義語。LLM 使用）
 → ハイブリッド検索（ベクトル + 全文）※RLS 下で実行
 → 有効性の解決 resolveCurrent()
 → 再ランキング
 → 結果（チャンク + メタデータ）
```

**`resolveCurrent()` の仕様**
- `superseded` のノートは本流の結果から外し、`superseded_context` として別枠で返す（置き換え先ノートの ID を付ける）
- 置き換え先が閲覧できない場合は、元ノートを `active` 扱いにはせず「より新しい版がある可能性」とだけ示す（相手ノートの情報は出さない）
- 同じテーマで `active` なノートが複数あり、`contradicts` 関係（confirmed または proposed）がある場合は `conflicts` として返す
- `proposed` の置き換え関係を持つノートには `possibly_outdated: true` を付ける

### 6.2 置き換え関係の推定と承認（AI が推定し、人が承認）

**推定（バックグラウンド）**
1. ノートの保存（`active` への変更、または `active` ノートの更新）をトリガーにジョブを起動
2. embedding 類似度で候補ノートを最大 N 件（初期値 5）抽出
3. LLM で各候補を判定し、`supersedes / contradicts / related / none` と確信度・理由を出力
4. 確信度がしきい値（初期値 0.7）以上のものを `note_relation(state=proposed, proposed_by=ai)` として保存

**承認（人間のみ）**
- 保存直後のノート画面に、バナーで「このノートは『旧・出張規程』を置き換えるものですか？」と表示。「はい」「いいえ」「後で」のワンクリック
- ヘッダーに未処理の提案件数を表示し、提案一覧（インボックス）から一括処理できる
- 承認時は 2 つのノートを並べる比較ビューを開けるようにする（差分をハイライト）
- 承認・却下できるのは、**両方のノートの編集権限を持つユーザー**のみ

**エージェントによる提案**
- サーバ MCP / WebMCP のエージェントも `propose_relation` で提案できる（`proposed_by=agent`）
- エージェントは承認できない。WebMCP では、確認ダイアログを開くところまでをツールで行い、確定は人間のクリックで行う

### 6.3 回答の合成（サーバ・クライアントの両方に対応）

**回答の契約（両方式共通、変更禁止）**
- 回答内のすべての主張に、根拠ノート（ID、タイトル、該当チャンク）を付ける
- 根拠が見つからない場合は、推測で答えず「見つからなかった」と返す。近い情報があれば併記する
- `superseded` のノートは根拠に使わない。関連する場合は「以前は〜だった（旧情報）」として区別して示す
- `conflicts` がある場合は、どちらかに寄せずに両論と各根拠を示す
- `possibly_outdated` のノートを根拠に使った場合は、その旨を明示する

**方式 1：サーバ合成（`ask`）**
- サーバが §6.1 の検索を行い、Claude を呼んで回答を合成して返す
- 主な利用者：Web UI の質問欄、LLM を持たない軽量クライアント
- 返り値は §7.3 の `Answer` 型

**方式 2：クライアント合成（`search_knowledge`）**
- サーバは §6.1 の結果をそのまま返し、合成はクライアント側のエージェントが行う
- 返り値に `synthesis_guidelines`（上の「回答の契約」を短く要約した文字列）を含め、クライアントのエージェントが同じ契約に従えるようにする
- 主な利用者：Claude Code、Claude Desktop、ブラウザ内アシスタント

どちらの方式でも、検索と有効性判定は同じ関数を通すこと。

### 6.4 経緯の再構成（健太のユースケース）

- `get_note_lineage(note_id)`：置き換えの連鎖を時系列で返す（閲覧できるノートのみ）
- `ask` で「なぜ」「経緯」を問う質問には、関連ノートを日付順に並べ、判断が変わった時点を明示する回答形式を使う

## 7. MCP ツール定義

### 7.1 サーバ MCP ツール

| ツール | 種別 | 説明 |
|---|---|---|
| `search_knowledge` | 読み取り | §6.1 の検索結果を返す（クライアント合成用） |
| `ask` | 読み取り | サーバ合成の回答を返す |
| `get_note` | 読み取り | ノート本文とメタデータ |
| `get_note_lineage` | 読み取り | 置き換えの連鎖 |
| `list_pending_relations` | 読み取り | 自分が処理できる未承認の提案 |
| `create_note` | 書き込み | ノートを作成（既定 `visibility=private`、`status=draft`） |
| `update_note` | 書き込み | ノートを更新（編集権限が必要） |
| `propose_relation` | 書き込み | 置き換え・矛盾・関連の提案 |

**サーバ MCP に含めないもの**：`resolve_relation`（承認）、公開範囲の変更、ノートの削除。これらは人間が UI で行う。

### 7.2 WebMCP ツール

サーバ MCP の読み取り系ツールに加えて、画面操作用のツールを登録する。

| ツール | 説明 |
|---|---|
| `get_current_context` | 現在開いている画面（ノート ID、検索クエリ、選択範囲） |
| `open_note` | 指定ノートを開く |
| `open_compare_view` | 2 つのノートの比較ビューを開く |
| `highlight_citation` | 回答中の引用に対応する箇所をハイライト |
| `request_relation_approval` | 承認ダイアログを開く。確定は人間のクリックのみ |
| `draft_note` | エディタに下書きを流し込む。保存は人間が行う |

- ログインしていない状態ではツールを登録しない
- 画面遷移に合わせて `get_current_context` の返り値を更新する

### 7.3 主要な型

```ts
type SearchResult = {
  hits: Hit[];                        // active なノートのチャンク
  superseded_context: Hit[];          // 置き換え済みノート（旧情報）
  conflicts: Conflict[];
  synthesis_guidelines: string;
};

type Hit = {
  note_id: string;
  title: string;
  chunk: string;
  status: "active" | "superseded";
  updated_at: string;
  effective_from?: string;
  possibly_outdated: boolean;
  superseded_by?: string;             // 閲覧可能な場合のみ
  score: number;
};

type Conflict = {
  note_ids: string[];
  summary: string;
  relation_state: "proposed" | "confirmed";
};

type Answer = {
  answer: string;                     // 引用マーカー [1] [2] を含む
  citations: { marker: string; note_id: string; title: string; chunk: string }[];
  outdated_mentions: { note_id: string; title: string; note: string }[];
  conflicts: Conflict[];
  not_found: boolean;
};
```

## 8. ユースケースと受け入れ条件

### UC1 美咲：散らばった規程から現行の答えを得る

> 「出張の宿泊費の上限はいくら？」
> 関連：旧規程（superseded）、チャット転記メモ（active）、改定通知（active）

- [ ] 回答は現行の上限額を 1 つ示し、根拠として改定通知を引用する
- [ ] 旧規程の金額は「旧情報」として区別され、現行の答えとしては扱われない
- [ ] 転記メモと改定通知の金額が食い違う場合、両方が根拠付きで示される
- [ ] 美咲が閲覧できない役員向け規程は、存在も含めて回答に現れない

### UC2 健太：決定の経緯をたどる

> 「決済サービスをなぜ A 社にしたんだっけ？」
> 関連：議事録 3 回分、比較表、一度覆った判断

- [ ] 回答は日付順に経緯を示し、判断が変わった時点を明示する
- [ ] 現時点で有効な決定が最後に明示される
- [ ] 各段階に根拠となる議事録が引用される

### UC3 共通：保存時の置き換え提案

- [ ] 新しい規程ノートを `active` にすると、1 分以内に旧規程との置き換え提案がバナーで表示される
- [ ] 「はい」を押すと旧ノートが `superseded` になり、以後の検索で旧情報扱いになる
- [ ] 「いいえ」を押すと提案は `rejected` になり、同じペアは再提案されない
- [ ] 片方のノートの編集権限がないユーザーには、承認ボタンが表示されない

### UC4 翔：Claude Code から仕様を参照する

- [ ] Claude Code から `search_knowledge` を呼ぶと、`synthesis_guidelines` を含む構造化データが返る
- [ ] `propose_relation` で提案を作れるが、承認はできない
- [ ] 翔が閲覧できない private ノートは結果に含まれない

### UC5 ブラウザ内アシスタント：画面文脈で動く

- [ ] 美咲がノートを開いた状態で「これって最新？」と聞くと、アシスタントが `get_current_context` で対象ノートを特定し、置き換え関係と矛盾の有無を答える
- [ ] 必要に応じて `open_compare_view` で比較ビューを開ける
- [ ] 承認は `request_relation_approval` でダイアログを開くまでで、確定には美咲のクリックが必要

## 9. 評価とテスト

### 9.1 フィクスチャ

`fixtures/` に以下のシナリオデータを用意し、シードスクリプトで投入できるようにする。

- 出張規程シナリオ（UC1）：旧規程・新規程・転記メモ・役員向け規程（private）
- 決済サービス選定シナリオ（UC2）：議事録 3 本、比較表、覆った判断
- 権限シナリオ：private / shared / workspace のノートを 3 ユーザーで交差させたもの

### 9.2 必須テスト

- **権限の漏洩テスト**：全ツール・全入口について、閲覧できないノートの ID・タイトル・本文・件数が返り値に含まれないこと
- **回答の契約テスト**：UC1・UC2 の質問に対し、§6.3 の契約（引用あり、旧情報の区別、矛盾の提示）が守られること。LLM 出力は構造化出力で検証する
- **状態遷移テスト**：`superseded` への遷移が承認経由でしか起きないこと
- **入口の一貫性テスト**：同じ質問に対し、Web UI・サーバ MCP・WebMCP の `search_knowledge` が同じ結果を返すこと

### 9.3 成功指標（リリース後に計測）

| 指標 | 目標（仮） |
|---|---|
| 質問から回答表示までの時間 | p50 で 5 秒以内 |
| 回答の引用がクリックされる率 | 計測のみ（信頼性の指標として追う） |
| AI 提案の承認率 | 60% 以上（下回る場合はしきい値を調整） |
| 旧情報を現行として回答した件数（評価セット） | 0 件 |

## 10. 実装ステップ

各ステップの完了条件を満たしたらコミットし、次へ進む。

1. **雛形**：Next.js + Supabase のプロジェクト作成、認証、CI（lint / 型チェック / テスト）
   - 完了条件：ログインしてダッシュボードが表示される
2. **スキーマと RLS**：§4 のテーブル、§5 の RLS ポリシー、シードスクリプト
   - 完了条件：§9.2 の権限テストのうち DB 層のものが通る
3. **ノートの CRUD とエディタ**：作成・編集・公開範囲の設定・共有・版履歴
   - 完了条件：3 種類の visibility が UI から設定でき、権限通りに見え方が変わる
4. **検索パイプライン**：チャンク化、embedding、ハイブリッド検索、`resolveCurrent()`

## 11. スコープ外（v1）

| 項目 | 理由 |
|---|---|
| リアルタイム共同編集 | 小規模チームでは優先度が低く、実装コストが高い |
| 外部サービスからの自動取り込み（Slack、Drive 等） | まずは ankb 内のノートで価値を検証する |
| view / edit より細かいロール | ノート単位の公開範囲で足りるかを先に確認する |
| ネイティブモバイルアプリ | レスポンシブ Web で対応する |
| ノートの物理削除 | 経緯の追跡を優先し、v1 は `archived` のみ |
